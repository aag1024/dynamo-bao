(static) _modelPrefixPkMode() → {"legacy"|"migrating"|"tenant-scoped"}

Description:

  • Migration mode for models whose primary key partition is modelPrefix (i.e. PrimaryKeyConfig("modelPrefix", <idField>)). For these models the base-table partition key historically was the bare model prefix (e.g. "apin"), which is GLOBAL — every tenant's rows share one partition and a by-id find() is not tenant-isolated. Tenant-scoping it ([tenant]#apin) closes that hole, but flipping the on-disk key atomically strands every existing row. This flag drives a safe expand/migrate/contract rollout:

    "legacy" - bare modelPrefix pk. Identical to historical behavior. "migrating" - writes/reads use the tenant-scoped pk, but reads fall back to legacy key shapes so nothing is stranded while a backfill relocates rows. Updates write in place at the row's current key; deletes already target the loaded key. "tenant-scoped" - tenant-scoped pk only; fallback off (post-migration).

    The tenant-scoped key is the clean [tenant]#modelPrefix (e.g. [tenant]#apin). Both the write path (_getDyKeyForPkSk) and the query path (queryByPrimaryKey / primary-key queryByIndex) derive it from the same _formatPrimaryPartition helper, so writes/finds/queries stay consistent.

    Set via initModels config: { keyMigration: { modelPrefixPkMode: "..." } }. Only affects models with primaryKey.pk === "modelPrefix". When tenancy is enabled, those models must set the mode explicitly so new apps choose the isolated key format intentionally and existing apps opt into legacy behavior deliberately.

    Known limitations during the "migrating" window (both resolve once the backfill completes and you switch to "tenant-scoped"):

    • Primary-key PARTITION queries (queryByPrimaryKey / a primary-key queryByIndex) read only the canonical partition, so rows not yet relocated by the backfill are not returned. By-id find() is unaffected (it falls back), and GSI queries are unaffected (GSI keys never change).
    • create() with an EXPLICIT primary id that already exists at a legacy key is not detected as a duplicate (the attribute_not_exists guard only checks the canonical key). Models with auto-assigned ids (the default) cannot hit this.

(static) queryByIndex(indexName, pkValue, skCondition, options) → {Promise.<Object>}

Description:

  • This is the primary method for querying data via a named index or primary key. If possible, you should always specify a sort key condition using skCondition. This will use dynamodb's index to query the data without scanning the partition.

    Optionally, you can specify a filter condition to further narrow down the results. Please note that a filter condition will scan anything in the partition that matches the skCondition, so if you haven't specified a skCondition, this will scan the entire partition (and consume more capacity units). However, there may also be times when this works without issue and is more efficient than adding another index and paying for the write overhead of the index.

Source:
  • mixins/query-mixin.js, line 141
Example
// Basic query
const results = await Model.queryByIndex('statusIndex', 'active');

// Query with sort key condition
const results = await Model.queryByIndex('dateIndex', 'user123', {
  createdAt: { $between: [startDate, endDate] }
});

// Query with pagination
const results = await Model.queryByIndex('statusIndex', 'active', null, {
  limit: 10,
  startKey: lastEvaluatedKey
});

// Query with related data
const results = await Model.queryByIndex('userIndex', userId, null, {
  loadRelated: true,
  relatedFields: ['organizationId']
});

(static) relocateToCanonicalKey(primaryId, optionsopt) → {Promise.<{relocated: boolean, from: ?string, to: string, reason: (string|undefined)}>}

Description:

  • Relocate a single record's base-table row from a legacy pk === "modelPrefix" key to the current canonical key. This is the per-record primitive used to back-fill the keyMigration.modelPrefixPkMode migration.

    Must be called in "migrating" mode and under the row's tenant context (so getTenantId() resolves the tenant the canonical [tenant]#prefix key is built from). The row's full item is copied verbatim to the canonical key (a conditional Put that won't clobber an existing canonical row), then the legacy row is deleted. GSI entries and unique-constraint pointers are unaffected (their keys never change; the pointer's relatedId is the unchanged logical id), so only the base row moves.

    Idempotent and safe to re-run: a row already at the canonical key is left alone; a stale legacy row left behind by an interrupted run is cleaned up.

(async, static) searchAll(terms, optionsopt) → {Promise.<{items: Array.<BaoModel>, cursor: (string|null)}>}

Description:

  • Search a searchable: { fields: [...] }-configured iterable model by substring(s) of _searchText. Each term becomes one contains(_searchText, :term) predicate. Multiple terms are combined with $and (default) or $or. Each term is normalized with the same rules used to build _searchText at write time, so user input matches what's stored.

    Reads from the bucketed iter_search_index GSI. By default fans out across every bucket in parallel; sequential mode is available via parallel: false. Returns one page of results plus an opaque cursor for resumption. To paginate, pass the cursor back on subsequent calls; cursor === null indicates the search is exhausted.

Source:
  • model.js, line 450
Example
// First page
const { items, cursor } = await Post.searchAll(["alice"], { limit: 50 });
// "Load more"
const next = await Post.searchAll(["alice"], { limit: 50, cursor });
// Drain everything
let cur = null, all = [];
do {
  const page = await Post.searchAll(["alice"], { limit: 100, cursor: cur });
  all.push(...page.items);
  cur = page.cursor;
} while (cur);
